Matrix multiply (GEMM)

C := α op(A) op(B) + β C in several forms:

  • gemm! — the dense entry point, in output-first (gemm!(C, A, B; alpha, beta)) or BLAS (gemm!(transA, transB, alpha, A, B, beta, C)) argument order.
  • gemmEx! — storage and accumulation types chosen separately.
  • gemm_batched! and gemmEx_batched! — many independent products in one call, from a vector of matrices or a 3-D strided array.
  • Grouped GEMM — batches of products with different shapes.
  • recgemm! — recursive GEMM; its mixed-precision method is documented under Mixed-precision BLAS.
  • GEMM_ADD! / GEMM_SUB! — the tiled KernelAbstractions kernel.

NextLA.gemm! — Function
gemm!(C, A, B; alpha=true, beta=false, kwargs...)

Compute C := alpha * A * B + beta * C in place.

gemm! is the common NextLA dispatch point for dense and structured matrix products. Dense matrix products forward to LinearAlgebra.mul!, while structured matrix types provide specialized methods.

Examples

julia> A = rand(1024, 1024); B = rand(1024, 1024); C = rand(1024, 1024);

julia> C0 = copy(C);

julia> gemm!(C, A, B; alpha=2.0, beta=0.5);   # C = 2AB + C/2

julia> C ≈ 2.0 * A * B + 0.5 * C0
true

NextLA.gemm! — Method
gemm!(transA, transB, alpha, A, B, beta, C) -> C

The BLAS argument order: C := alpha * op(A) * op(B) + beta * C, where op is the identity, transpose or adjoint for 'N', 'T' or 'C'.

vicki-development called GEMM this way through src/wrappers.jl, a CUDA/AMD shim this repo does not take. Here it forwards to the output-first method, so it runs on every backend and reaches cuBLAS/rocBLAS through mul! on GPU arrays.

Examples

julia> A = rand(1024, 1024); B = rand(1024, 1024); C = zeros(1024, 1024);

julia> gemm!('T', 'N', 1.0, A, B, 0.0, C);   # C = Aᵀ B

julia> C ≈ transpose(A) * B
true

NextLA.gemmEx! — Method
gemmEx!(transA, transB, alpha, A, B, beta, C; compute_type=...)

Compute the matrix product

C := alpha * op(A) * op(B) + beta * C

and store the result in C.

gemmEx! is an advanced NextLA API for backends that support mixed-type GEMM where the result storage may differ from the operand storage. It is available unqualified (it is exported) and as NextLA.gemmEx!.

op(A) and op(B) are determined by transA and transB, which may be:

  • 'N': no transpose
  • 'T': transpose
  • 'C': adjoint

Notes

  • The accumulation type can be selected explicitly with compute_type; by default default_compute_type chooses it from the storage types of A, B and C. alpha and beta take no part and are converted to it.
  • Mixed storage and compute types are a CUDA and AMDGPU feature. The CPU accepts any combination, accumulating in compute_type. oneAPI and Metal have no gemmEx! and throw for every signature, same-type ones included.
  • If a backend does not support a requested storage and compute type combination, backend-specific errors may be raised.
  • Algorithm selection and backend-specific math modes are out of scope for this API.

Examples

julia> A = rand(Float16, 1024, 1024); B = rand(Float16, 1024, 1024);

julia> C = zeros(Float32, 1024, 1024);   # Float16 operands, Float32 result

julia> gemmEx!('N', 'N', 1.0, A, B, 0.0, C; compute_type=Float32);

julia> C ≈ Float32.(A) * Float32.(B)
true

Compute types and alignment

NextLA.GEMM_COMPUTE_TYPES — Constant
GEMM_COMPUTE_TYPES

compute_type values inferred or used internally by the advanced NextLA.gemmEx! and NextLA.gemmEx_batched! APIs.

compute_type is the Julia type used to request the GEMM accumulation type. These are plain Julia types, not backend-specific math modes such as TF32 or other fast-math settings.

NextLA separates its primary BLAS surface from the advanced Ex interfaces:

  1. Ordinary dense GEMM is intentionally left to the backend itself, e.g. C = A * B for dense matrices.
  2. gemm_batched! provides the batched GEMM surface used by TLR algorithms.
  3. NextLA.gemmEx! and NextLA.gemmEx_batched! are advanced APIs for mixed-type GEMM where the result storage may differ from the operand storage.

compute_type is chosen from the storage types of A, B and C by default_compute_type; alpha and beta take no part and are converted to it. Support for the chosen combination depends on the backend.

The CPU column is served by BLAS. Single-matrix gemmEx! is the exception: there is no CPU GEMMEx primitive, so a triple BLAS accepts goes to BLAS.gemm! and everything else is accumulated in compute_type and rounded once on store. The batched and precision entry points do not extend that to the CPU – they take what BLAS takes and raise ArgumentError for the rest. The CPU has no half-precision arithmetic, so a wide accumulation there is a convenience, not a speed-up.

A throws above is a vendor limitation or an unverified path rather than an oversight. Neither oneMKL nor MPS exposes a pointer-array batched GEMM or a heterogeneous grouped GEMM, and TF32 is CUDA hardware. gemmEx! on oneAPI and Metal, and Metal's vector-of-matrices batch, throw because no device was available to verify a same-type path; a 3-D batch is the supported Metal form. supports_pointer_batched and supports_grouped_gemm answer for the backend, so a caller can ask before committing to a path.

The oneAPI and Metal entries are written from the vendor APIs and have never been executed – neither device was available during the integration.

NextLA.aligned_leading_dimension — Method
aligned_leading_dimension(T, m) -> Int

Smallest leading dimension >= m that keeps every column of a column-major dense T matrix 16-byte aligned.

Allocate the padded array and take a logical view over the first m rows:

using NextLA, CUDA
n = 1024
ld = aligned_leading_dimension(Float16, 4097)   # 4104
store = CuArray{Float16}(undef, ld, n)
C = view(store, 1:4097, :)                      # stride(C, 2) == 4104

A column offset costs c * ld * sizeof(T) bytes, so an aligned ld makes every column start aligned regardless of which column a panel begins at. Row offsets are ld-independent — those are governed by the tile extent instead, which is what is_gemm_aligned checks.

source
NextLA.default_compute_type — Method
default_compute_type(alpha, A, B, beta, C)

Return the default compute_type inferred by NextLA for mixed-type GEMM.

The rule is intentionally simple and backend-agnostic:

  • Float16 defaults to Float16
  • Float32 defaults to Float32
  • Float64 defaults to Float64
  • integer inputs default to Int32
  • complex inputs follow the corresponding real compute type

Only the storage types of A, B and C decide. alpha and beta are accepted for the signature but take no part, so an untyped literal such as 0.5 on Float32 data cannot raise the compute type to Float64.

Backends may still reject unsupported storage and compute type combinations.

Examples

julia> A = rand(Float16, 1024, 1024); C = zeros(Float32, 1024, 1024);

julia> default_compute_type(1.0, A, A, 0.0, A)   # the Float64 scalars take no part
Float16

julia> default_compute_type(1.0, A, A, 0.0, C) === Float32
true

NextLA.gemm_alignment_quantum — Method
gemm_alignment_quantum(T) -> Int

Number of T elements spanning 16 bytes — the granularity at which offsets into a dense operand remain 16-byte aligned.

cuBLAS documents 16-byte alignment of pointers, leading dimensions and the m extent as a performance condition for Tensor Core kernels, not a legality one. Unaligned operands compute correct results but select a slower kernel; measured cost is ~2.2-2.5x for grouped GEMM on H100 and ~1.9-2.2x on Turing. Size tiles and leading dimensions against this quantum to keep the fast kernels selected.

Tquantum
Float16/BFloat168
Float324
Float642

See also aligned_leading_dimension, is_gemm_aligned.

Examples

julia> gemm_alignment_quantum(Float16)
8

julia> gemm_alignment_quantum(Float64) * sizeof(Float64) == 16
true

is_gemm_aligned(T, n) -> Bool

Whether n elements of T span a whole number of 16-byte units.

Applied to a nominal tile size this reports whether tile boundaries land on aligned addresses (tile row i of a dense output starts at element offset (i-1) * bm, which is independent of the leading dimension). Applied to a leading dimension it reports whether columns do.

Batched GEMM

NextLA.BatchPtrDescriptor — Type
BatchPtrDescriptor(ptrs)
BatchPtrDescriptor(batch::AbstractVector{<:AbstractMatrix})

A device array of matrix base pointers built once and reused across many batched GEMM calls (via gemm_batched_ptrs!/gemmEx_batched_ptrs!), in contrast to the transient pointer arrays the Vector-of-matrix gemm_batched!/gemmEx_batched! methods build and free on every call.

A descriptor carries only addresses, no shape/element-type/leading-dimension information — callers supply a fresh, cheap representative Aref/Bref/Cref view at each call to size that call's GEMM. Slot k is stable across calls: if which logical batch member occupies slot k changes (e.g. active-prefix packing retiring a converged member), that must be expressed with swap_batch_ptrs!, which moves addresses between slots, never by physically reordering the pointed-to data or by rebuilding the descriptor.

The caller owns the descriptor's lifetime and must keep the pointed-to storage alive for as long as the descriptor is used; unlike the transient pointer arrays built by the Vector-of-matrix methods, nothing frees a BatchPtrDescriptor's pointer array automatically.

source
NextLA.gemmEx_batched! — Method
gemmEx_batched!(transA, transB, alpha, A, B, beta, C; compute_type=...)

Compute a mixed-type batched matrix product.

Each batch entry applies

C[i] := alpha * op(A[i]) * op(B[i]) + beta * C[i]

where op(A) and op(B) are determined by transA and transB.

gemmEx_batched! is an advanced NextLA API for batched mixed-type GEMM. It is available as NextLA.gemmEx_batched! and is not part of the primary exported surface.

Notes

  • The accumulation type can be selected explicitly with compute_type; by default it is inferred from alpha, beta, and the operand/result element types using default_compute_type.
  • Same-type batched calls may fall back to gemm_batched! on backends that do not expose a mixed-type batched GEMM primitive.
  • Mixed-type batched GEMM is currently implemented for CUDA and AMDGPU.
  • If a backend does not support a requested storage and compute type combination, backend-specific errors may be raised.
  • Algorithm selection and backend-specific math modes are out of scope for this API.

Examples

julia> A = [rand(1024, 1024) for _ in 1:4]; B = [rand(1024, 1024) for _ in 1:4];

julia> C = [zeros(1024, 1024) for _ in 1:4];

julia> NextLA.gemmEx_batched!('N', 'T', 1.0, A, B, 0.0, C);   # same type: allowed on the CPU

julia> all(C[i] ≈ A[i] * transpose(B[i]) for i in 1:4)
true

NextLA.gemm_batched! — Method
gemm_batched!(transA, transB, alpha, A, B, beta, C)

Compute a batched matrix product and store the result in C.

Three storage forms are supported:

  • AbstractArray{T,3} for strided batches
  • AbstractVector of matrices for pointer batches

NextLA.GEMM_ADD! — Function
GEMM_ADD!(A, B, C, scale=1) -> C

C .+= scale * A * B. A or B may be a Transpose or an Adjoint. A Float16 C accumulates in Float32; a result beyond floatmax(Float16) is stored as Inf. Shapes that do not fit throw DimensionMismatch.

Usage examples

Both argument orders of gemm! make the same update; the BLAS order takes the transposes as flags, the output-first order as transpose/adjoint wrappers.

using NextLA, LinearAlgebra

A = rand(2048, 1024)
B = rand(2048, 1024)
C1 = rand(1024, 1024)
C0 = copy(C1)
C2 = copy(C1)

gemm!('T', 'N', 2.0, A, B, 1.0, C1)                    # BLAS order: C1 = 2 Aᵀ B + C1
gemm!(C2, transpose(A), B; alpha = 2.0, beta = 1.0)    # output first, same update
C1 ≈ C2 ≈ 2.0 * transpose(A) * B + C0

# output

true

gemmEx! multiplies Float16 matrices with a Float32 accumulation and rounds once on store; recgemm! picks that accumulation by itself.

using NextLA, LinearAlgebra

A = rand(Float16, 2048, 2048)
B = rand(Float16, 2048, 2048)
C1 = zeros(Float16, 2048, 2048)
C2 = zeros(Float16, 2048, 2048)

gemmEx!('N', 'N', 1.0, A, B, 0.0, C1; compute_type = Float32)   # accumulate in Float32
recgemm!(1.0, A, B, 0.0, C2)                                    # chooses Float32 by itself
C1 ≈ C2 && isapprox(C1, Float64.(A) * Float64.(B); rtol = 1e-3)

# output

true

gemm_batched! takes a 3-D strided batch, where an operand with batch count 1 is shared by every member, or a vector of matrices.

using NextLA, LinearAlgebra

A = rand(1024, 1024, 8)
B = rand(1024, 1024, 1)        # batch count 1: one B shared by every member
C = zeros(1024, 1024, 8)
gemm_batched!('N', 'N', 1.0, A, B, 0.0, C)

As = [rand(1024, 1024) for _ in 1:4]
Bs = [rand(1024, 1024) for _ in 1:4]
Cs = [zeros(1024, 1024) for _ in 1:4]
gemm_batched!('N', 'T', 1.0, As, Bs, 0.0, Cs)

all(C[:, :, i] ≈ A[:, :, i] * B[:, :, 1] for i in 1:8) &&
    all(Cs[i] ≈ As[i] * transpose(Bs[i]) for i in 1:4)

# output

true

Grouped GEMM runs products of different shapes in one call, described by GroupedGemmTasks (a loop on the CPU, one grouped call on CUDA).

using NextLA, LinearAlgebra

shapes = [(1024, 2048, 512), (2048, 1024, 1024), (4096, 512, 1024)]   # (m, n, k) per member

         for (m, n, k) in shapes]

NextLA.precision_gemm_grouped!(tasks, NextLA.GEMMCompute{Float64}())
all(t.C ≈ t.A * t.B for t in tasks)

using NextLA, CUDA

# Float16 storage, Float32 accumulation: one cuBLAS GEMMEx call
A = CUDA.rand(Float16, 4096, 4096)
B = CUDA.rand(Float16, 4096, 4096)
C = CUDA.zeros(Float16, 4096, 4096)
gemmEx!('N', 'N', 1f0, A, B, 0f0, C; compute_type = Float32)

# a 3-D strided batch: one cuBLAS strided-batched call
Ab = CUDA.rand(Float32, 1024, 1024, 16)
Bb = CUDA.rand(Float32, 1024, 1024, 16)
Cb = CUDA.zeros(Float32, 1024, 1024, 16)
gemm_batched!('N', 'N', 1f0, Ab, Bb, 0f0, Cb)

NextLA.precision_gemm!('N', 'N', 1f0, X, Y, 0f0, Z, TF32())
