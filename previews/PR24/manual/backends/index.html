Backends and GPUs

NextLA writes its kernels once with KernelAbstractions.jl and picks the backend from the array it is given (KernelAbstractions.get_backend(A)). Vendor-specific code lives in package extensions under ext/, which Julia loads automatically when the matching GPU package is loaded:

ExtensionLoaded byVendor libraries used
NextLACUDAExtusing CUDAcuBLAS, cuSOLVER
NextLAAMDGPUExtusing AMDGPUrocBLAS, rocSOLVER
NextLAoneAPIExtusing oneAPIoneMKL
NextLAMetalExtusing MetalMetal Performance Shaders

Without any GPU package, every routine runs on the CPU, calling LinearAlgebra.BLAS/LAPACK where they cover the element type and portable Julia kernels otherwise.

Usage

using NextLA, CUDA          # or AMDGPU, oneAPI, Metal

using LinearAlgebra
A = rand(Float32, 100, 100)
S = CuArray(A * A' + 100I)   # move the matrix to the GPU once

potrf_recursive!(S)          # runs on the GPU

The call is the same as on the CPU. Keep all operands on the same device: NextLA does not move data between host and device for you.

Notes:

  • gemmEx! with differing storage and compute types is a CUDA and AMDGPU feature; the CPU accepts any combination and accumulates in compute_type. oneAPI and Metal throw.
  • trsm! reaches cuBLAS/rocBLAS trsm! for Float32, Float64, ComplexF32 and ComplexF64 dense matrices; Float16, views and the other backends take the portable recursion.
  • potrf! has no generic device fallback, so on a backend without a wrapper (oneAPI) it throws instead of silently copying to the host. potrf_recursive! calls it at its leaves.
  • Float16 has no vendor SYRK, so recursive Cholesky in half precision uses recsyrk!.
  • cholesky_blocked! is GPU-only: on the CPU it throws and points to potrf!. tile_lu_factor! refuses the CPU because its kernels give wrong results there.
  • cuBLAS has no batched SYRK, so syrk_batched! loops single calls on CUDA; Metal has no SYRK at all, and its single-matrix syrk! can overwrite the other triangle.
  • The AMDGPU fast path of unified_rectrxm! compiles and is selected for ROCMatrix arguments, but has not been run on AMD hardware.
  • The QR tile kernels are not exported (call them as NextLA.geqrt! and so on). Their CUDA runs pass the test suite on Julia 1.10.

GEMM compute modes

For reduced-precision inputs, gemmEx! and its batched variants take a compute_type that sets the accumulation precision. default_compute_type picks one from the storage types of A, B and C, and GEMM_COMPUTE_TYPES documents the supported behaviour per backend. The precision-policy entry points such as precision_gemm_batched! take a compute mode instead, where TF32 requests TensorFloat-32 computation for Float32 operands.

Some vendor GEMMs need aligned leading dimensions; is_gemm_aligned, gemm_alignment_quantum and aligned_leading_dimension help allocate arrays that qualify.
